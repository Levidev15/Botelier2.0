Concrete change you need

Right now this is local-only:

await call_handler.cancel_call_pipeline(call_sid)

You need to wrap it:

await call_control.cancel_call(call_sid)

Where call_control.cancel_call() does:

1. Check if this process owns callSid
2. If yes, call local call_handler.cancel_call_pipeline(callSid)
3. If no, publish command to Redis channel for owning worker

Conceptually:

class DistributedCallControl:
    async def register_call(self, call_sid: str, worker_id: str):
        await redis.setex(f"call_owner:{call_sid}", 3600, worker_id)

    async def cancel_call(self, call_sid: str):
        owner = await redis.get(f"call_owner:{call_sid}")

        if owner == WORKER_ID:
            await local_call_handler.cancel_call_pipeline(call_sid)
            return

        await redis.publish(
            f"worker:{owner}:commands",
            json.dumps({
                "type": "cancel_call",
                "callSid": call_sid,
            })
        )

And each worker subscribes to its own command channel:

async def listen_for_worker_commands():
    async for message in redis_pubsub.listen():
        data = json.loads(message["data"])

        if data["type"] == "cancel_call":
            await call_handler.cancel_call_pipeline(data["callSid"])

        if data["type"] == "save_transcript":
            await call_handler.save_transcript_for_call(data["callSid"])
Your current frontend proxy is also a bottleneck

Your botelier/frontend/server.js proxies /api/ws/* using a raw TCP relay to BACKEND_URL.

That means production currently looks like:

Twilio
  |
  v
Next.js Node server on port 5000
  |
  v
FastAPI backend on localhost:3001

This works for one VM, but it is not ideal for scaling call traffic.

For production scaling, I would avoid sending Twilio media streams through the Next.js server. Put the voice workers behind a real load balancer directly:

Twilio
  |
  v
wss://voice.yourdomain.com/api/ws/call
  |
  v
ALB / NGINX / Fly proxy / Render private service / ECS service
  |
  +--> FastAPI voice worker 1
  +--> FastAPI voice worker 2
  +--> FastAPI voice worker 3

Keep your dashboard/frontend separate:

app.yourdomain.com  -> Next.js dashboard
api.yourdomain.com  -> REST API
voice.yourdomain.com -> WebSocket voice workers
Best deployment direction

For your code, I would not start by adding more Uvicorn workers inside one VM. That would make the callback-routing problem worse because each Uvicorn worker has its own separate call_handler.

Instead, I’d do:

1. Containerize the backend voice service
2. Run 2-3 replicas minimum
3. Add Redis
4. Register call ownership on WebSocket start
5. Route cross-worker commands through Redis Pub/Sub
6. Autoscale replicas based on active calls

What I would change first
Create a separate voice-worker deployment from your existing backend code. It only needs /api/ws/call, /api/calls/incoming, /api/calls/status, /api/calls/connect-complete, and transfer/recording callbacks.
Move active-call ownership into Redis when handle_call() starts:
call_owner:{callSid} = workerId
Make callback actions distributed, especially:
save_transcript_for_call
cancel_call_pipeline
is_pipeline_active
Stop relying on module-level singleton state for anything cross-request unless the request is guaranteed to hit the same worker. The socket itself must stay local, but ownership metadata must be shared.
Deploy behind a WebSocket-capable load balancer and autoscale by active calls.
My honest assessment

Your voice code is already structured around one pipeline per call, which is good. The main missing piece is distributed call control.

Right now:

Single VM: works
Multiple VMs: WebSocket connects will distribute, but lifecycle callbacks may hit the wrong worker

The fix is not a full rewrite. It is mostly adding:

Redis call registry
worker command channels
separate voice-worker deployment
load balancer
graceful draining

That gets you from “one VM owns all calls” to “many workers can each own live calls safely.”
