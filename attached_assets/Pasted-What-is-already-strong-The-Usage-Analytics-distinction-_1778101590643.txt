What is already strong
The “Usage ≠ Analytics” distinction is correct. This prevents cost reporting from getting tangled with AI performance reporting.

The raw usage dimensions are the right ones: Twilio voice minutes, LLM prompt/completion tokens, TTS characters, STT seconds, and SMS tokens.

Persisting at call completion is the right boundary. The existing voice lifecycle already funnels normal transcript persistence through CallLogger.complete_call(), so call-end billing snapshotting fits naturally there. 

STT duration can reasonably come from the AI conversation leg. CallLeg already stores leg_type, started_at, ended_at, and duration_seconds, and the logger updates the AI leg duration from call answer time when a call ends. 

Pipecat usage metrics are already enabled. The pipeline task is created with both enable_metrics=True and enable_usage_metrics=True, and existing code already handles MetricsFrame with LLMUsageMetricsData, which makes an observer-based billing collector plausible. 

Recharts is already installed, so the requested area chart does not require a new frontend dependency. 

Main issues I would fix before implementation
1. The task is too large for one ticket
This combines:

Database schema and seed data.

Pipecat metrics collection.

Cost computation.

Call-end persistence.

Account billing APIs.

Admin billing APIs.

Account dashboard UI.

Admin dashboard UI.

Billing rate management UI.

SMS usage aggregation.

That is a full feature epic, not a single implementation task. I would split it into 3–5 tickets so the backend snapshotting can be verified before building UI on top of it.

Recommended split:

Ticket A — Billing data model + call-end snapshot.

Ticket B — Account usage APIs.

Ticket C — Admin usage/rates APIs.

Ticket D — Account Usage UI.

Ticket E — Admin Usage + Rates UI.

This will reduce risk because the persistence layer is the most important part to get right.

2. The current persistence proposal is missing an itemized immutable snapshot
The task says call_logs should persist:

llm_prompt_tokens

llm_completion_tokens

tts_characters

estimated_cost_usd

That is useful, but it is not enough to support an auditable provider/resource breakdown later. If rates change after a call ends, you can preserve the total, but you cannot reliably reconstruct how much of that total was Twilio vs STT vs LLM vs TTS unless you also persist the line items used at call end.

I would add either:

Better option
A call_billing_items table:

id

call_log_id

account_id

provider

resource_type

quantity

unit_label

rate_per_unit

cost_usd

billing_rate_id

created_at

Acceptable simpler option
A JSONB column on call_logs, for example:

billing_breakdown JSONB

But a real line-item table is better for admin aggregation, sorting, CSV export, and auditability.

Without this, the UI requirement for “monthly summary cost card broken down by provider/resource type” depends on recomputation or inference rather than a true immutable snapshot.

3. The “historical costs are immutably snapshotted” language needs to be stricter
A billing_rates table with effective_from is good, but immutability requires that call completion stores the actual rate used, not just the total. Otherwise, future edits or deletes to billing_rates could make historical detail ambiguous.

I would explicitly require:

Billing rates are append-only for historical rows.

Editing a rate creates a new row with a new effective_from.

Completed calls persist the resolved rate_per_unit and cost_usd per resource.

The total on call_logs.estimated_cost_usd is derived from the persisted line items.

The existing database startup migration pattern is additive/idempotent and already has precedent for fail-fast schema assertions, so the proposed database work fits the project style. 

4. Be careful with cached greeting TTS
There is a subtle billing question around greetings. The current code can serve the greeting from cached PCM and explicitly skip live Deepgram TTS for that greeting path.  If the billing observer simply counts all spoken TTS text, it may overstate variable provider cost for cached greetings.

The task should define one of these policies:

Provider-cost policy: only count TTS characters that caused a live TTS provider request.

Amortized-cost policy: count cached greeting characters as platform usage even when the cache avoided a provider call.

Hybrid policy: track live TTS characters and cached TTS characters separately.

For cost-of-goods-sold, I recommend provider-cost policy first, because it matches real provider spend.

5. SMS usage statement needs verification
The task says SMS “already has tokens_used per message.” The model does have SMSMessage.tokens_used, and SMS analytics already sums it.  However, in the inspected SMS service path, OpenAI usage is logged but I did not find an assignment persisting tokens_used in sms_service.py. 

So I would adjust the ticket to say:

Confirm SMS token persistence. If tokens_used is not currently written, persist response.usage.total_tokens or prompt/completion token fields before including SMS in billing aggregates.

Otherwise, the Usage dashboard may show zero or partial SMS usage despite the column existing.

6. Route naming should match the existing frontend structure
The proposed “new frontend page at /usage” does not match the current dashboard route pattern. Existing account dashboard nav items live under /dashboard/..., for example /dashboard/analytics/calls and /dashboard/analytics/sms. 

I would make the account page:

/dashboard/usage

Admin page /admin/usage fits the existing admin routing pattern and nav structure. 

7. Add explicit permissions
The task mentions usePermissions.ts, but the actual permission source of truth is the backend permission catalog and default role templates. Current permissions include settings.billing, but there is no dedicated usage or billing_usage resource. 

I would add explicit permissions such as:

usage.view

usage.export

billing_rates.view

billing_rates.manage — platform-admin only or admin route guarded.

Backend account APIs should use the existing check_account_permission() pattern to prevent cross-tenant leakage. 

Recommended revised scope
I would rewrite the first implementation ticket as:

Capture immutable per-call billing snapshots for completed Twilio WebSocket voice calls. Add billing rate reference data, collect Pipecat LLM/TTS usage metrics during a call, derive STT seconds from the AI conversation leg and Twilio minutes from call duration, compute provider/resource line items at call end, persist both call-level totals and itemized billing rows, and expose backend account/admin read APIs for usage summaries. UI dashboards can follow in a separate ticket.

That gives you a strong foundation without mixing data correctness and UI polish in one task.

Suggested additions to “Done looks like”
I would add these acceptance criteria:

Every completed voice call has a billing snapshot containing:

total prompt tokens

total completion tokens

live TTS characters

STT seconds

Twilio billable minutes

itemized cost rows by provider/resource

total estimated cost.

Billing line items store the resolved rate used at call end.

Rate edits do not mutate historical call costs.

Cached greeting TTS is either excluded from live TTS provider cost or tracked separately.

SMS tokens_used persistence is verified or implemented before SMS is included in usage totals.

Account usage routes enforce tenant isolation.

Admin usage routes require platform-admin access.

/dashboard/usage is used for account UI, not /usage.

CSV export uses persisted snapshots, not recomputed estimates.

Verdict
Good idea, good product direction, but not quite implementation-ready as a single task.

I would approve it after these changes:

Split it into backend snapshot/API and frontend UI phases.

Add itemized billing snapshots.

Define cached TTS billing behavior.

Verify or implement SMS token persistence.

Use /dashboard/usage.

Add explicit usage/billing permissions.
